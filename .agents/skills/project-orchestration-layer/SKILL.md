# Project Orchestration Layer

## 调用条件
- 仅在用户显式调用后生效。
- 不依赖关键词、分支名或上下文猜测触发。

## 角色边界
- 默认只做编排，不直接写业务代码。
- 在 `main` 一律禁止直接修改业务代码（包括小改动/顺手修复）。
- 业务代码改动必须派发到 `worktree-1/2/3` 槽位执行。
- 并行上限固定为 `3`，与 `worktree-1/2/3` 一一对应。
- 所有实现默认全量更新，不留兼容层；如有必要需同步更新相关文档。

## Skill 使用边界
- 编排层无需加载不必要的 skill，仅在当前任务确实需要时调用。
- 不以槽位 skill 使用策略或能力对比作为编排触发与执行依据。

## 执行前硬闸门
- 触发时机：任何编辑动作前必须执行（`Write/Edit/apply_patch/sed -i/提交前暂存` 均算编辑动作）。
- 必检命令：`git rev-parse --abbrev-ref HEAD` 与 `pwd`；两项结果必须同时证明当前在 `~/Projects/mimikit-worktree-{1,2,3}` 且分支为 `worktree-{1,2,3}`。
- 放行条件：仅当“目录命中槽位 + 分支命中槽位”同时成立，才允许进入实现流程。
- 拒绝条件：若处于 `main` 或非槽位，立即切换为“仅编排模式”；仅允许任务拆解/派发/状态汇报，禁止任何实现与提交。

## 防漂移机制
- 每轮回复必须显式声明：`模式=<编排|实现> | 分支=<branch> | 槽位=<worktree-x|none>`。
- 声明缺失、字段不全、或状态与硬闸门不一致：本轮自动降级为“仅编排模式”，禁止进入实现。
- 上下文切换后（切分任务、切槽位、准备编辑）必须重新执行硬闸门，不得复用旧结论。
## 越界复盘与防复发规则
- 已知根因：把临时修复误判为编排动作，且编辑前未确认槽位，导致在 `main` 直接实现。
- 防复发主规则：未通过硬闸门前，任何“实现型动作”一律不可执行。
- 违例判定：`main` 出现业务实现 diff（新增/修改/删除）即视为越界，不以改动大小豁免。
## 里程碑前置检查清单
1. 分配前
- 当前为编排层触发态（用户明确要求，不依赖分支名）。
- `worktree-1/2/3` 均可访问，槽位职责与文件边界无交叉。
- 任务卡字段完整：目标、文件边界、验收命令、禁止项、`任务编号/当前步骤/已完成/下一步/阻塞` 摘要。
2. 编辑前
- 任一槽位接到新任务卡后，第一步必须执行 `pnpm run wt-rebase`；与 `main` 同步成功前禁止编辑。
- 已执行并通过硬闸门（目录与分支双命中槽位）。
- 本次回复已声明 `模式/分支/槽位` 且与硬闸门一致。
- 若任一不满足：停止实现，回到编排派发。
3. land 前（落地前）
- 已执行 `review-code-changes`（覆盖 `lint/type-check/test`）且结论通过；未通过禁止 `wt-land`。
- 受影响测试已执行并通过；失败项已记录且阻塞 `wt-land`。
- 槽位中无需做提交或手动提交，直接执行 `pnpm run wt-land -- --message "task-..."` 提交当前工作区全部变更；`--message` 需可追溯到槽位任务卡 ID，且冲突必须在该步处理。
- 无跨槽位依赖时，任务完成且门禁通过后立即自动执行 `wt-land`，无需额外等待、无需用户二次确认；有依赖时按依赖拓扑顺序串行 `wt-land`，不得以 `main` 或其他槽位状态跳过本槽位门禁。
## 违例自动处置流程
1. 立即停止：发现 `main` 实现改动后，立刻停止一切编辑与提交动作。
2. 立即回滚：仅回滚本次越界实现改动到 `HEAD` 干净状态，不影响他人既有改动。
3. 记录根因：最少记录 `触发任务`、`越界文件`、`为何绕过硬闸门`、`防再发措施`。
4. 重新派发：生成新的槽位任务卡并指派到 `worktree-1/2/3`（含边界与验收命令）。
5. 恢复执行：从“执行前硬闸门”重新开始，未通过前不得恢复实现。
## 低 Token 协议
- 新建 agent 必须设置 `fork_context=false`，每个 agent 只发最小任务卡。
- 任务卡最小字段：目标、文件边界、验收命令、禁止项、`任务编号/当前步骤/已完成/下一步/阻塞` 摘要。
- multi agent 在任务完成后立刻关闭，禁止跨任务复用。
- 对已启动子进程/agent 的中断先评估浪费，默认不中断；仅在阻塞或目标已变化时中断，且必须记录中断原因与成本。
- 槽位执行默认“少中断 + 继续推进”：非阻塞且目标未变更时持续推进；预期外文件改动先记录影响，冲突集中在 `wt-land` 阶段处理。
- 对 token 极度敏感：优先最小输入、最少轮次，避免重复上下文与无效轮询。
- 编排层默认走低耗时路径：先做最小必要验证再推进；高耗时任务（`review-code-changes` 全量检查/大范围扫描/长轮询）延后到收敛或明确阻塞阶段；延后策略不得绕过收敛门禁或破坏依赖顺序。
- 状态回报只在里程碑触发：`完成`、`阻塞`、`待合并`。
- 对话中仅回：`files changed`、`diff --stat`、`3 条关键点`、`命令结论`；长日志写入本地文件，仅回路径与摘要。
- 槽位内优先跑受影响测试；收敛阶段由 `review-code-changes` 统一执行并给出 `lint/type-check/test` 结论。
## 工作流
- 槽位中任务完成后的固定收敛顺序：`1) 任务完成之后 → 2) review-code-changes 自检 → 3) pnpm run wt-land -- --message "task-..."（必须带 message；冲突必须在此步处理） → 4) 关闭子 agent`。
1. 预检：确认当前工作区信息（分支与目录）且 `worktree-1/2/3` 可访问。
2. 分配：按目录边界给 3 个 agent 分槽，避免交叉编辑；分配任务不要过细碎，同一块儿任务优先交给同一槽位统一执行；不要用两个槽位做同一个方向的任务（改代码与审查应在同一槽位一次分配完成）。
3. 同步：槽位接到新任务卡后首步执行 `pnpm run wt-rebase`，同步成功才可编辑；落地前若 `main` 有新提交需再执行一次。
4. 执行：agent 在各自槽位完成改动与自检。
5. 收敛：统一执行 `review-code-changes`（覆盖 `lint/type-check/test`）并以其结论判定是否可 `wt-land`；未通过禁止进入 `wt-land`。
6. 回主线：每个槽位直接执行 `pnpm run wt-land -- --message "..."`，无需手动提交；`wt-land` 负责提交该槽位当前工作区全部变更，不按“当前工作范围”筛选；预期外改动需记录并在合并阶段说明。无跨槽位依赖时，任务完成且门禁通过后立即自动 land，无需额外等待、无需用户二次确认；有依赖时按拓扑顺序串行 land。槽位改动 `land` 回 `main` 后不再重复执行额外门禁。
## 能力缺口处理
- 若出现 skill 生命周期问题（搜索/新增/替换/移除），立即调用 `audit-skill-lifecycle`。
- 若仅为实现细节问题，不触发 skill 生命周期治理，直接按现有能力推进。

## 汇报模板
- 进度：`{当前}/{总数}`
- 每槽位：`状态 | 改动文件数 | 关键风险(最多1条)`
- 合并阶段：`是否可 land | 阻塞项 | 下一动作`

## 禁止事项
- 禁止把完整会话上下文广播给全部 agent。
- 禁止重复输出相同背景信息与长篇日志。
- 禁止未过门禁直接 `wt-land`。
- 禁止忽略依赖关系执行 `wt-land`；存在依赖时必须按拓扑顺序串行，禁止与依赖链冲突的并发 land。
