# MIMIKIT 大规模重构最终方案（完整意图版，非实现细节）

## 1. 文档角色
本文件是后续大规模重构的最终目标文档，定义：
- 为什么重构
- 重构完成后系统应该具备什么能力
- 什么是必须守住的边界
- 如何判断重构是否成功

本文件不描述代码级实现方式，不规定函数、模块或技术细节。

## 2. 背景与问题陈述（来自本轮对话）
本次复盘与验证暴露了以下关键问题：

1. `focus` 概念可用度低
- 目前更像“上下文标签”，而不是“强约束工作线”。
- 多任务线下出现过路由漂移，用户需要反复纠偏。

2. 意图执行存在“确认不等于闭环”
- 部分场景出现“口头确认已处理，但缺少可验证动作证据”。

3. provider 波动导致调度损耗
- 失败/取消/重建在某些时段引发额外成本与时间浪费。

4. 上下文预算分配不合理
- 某些高价值信息被过度截断；
- 某些低价值上下文占用过多预算；
- 导致速度、成本、稳定性同时受影响。

5. 评分流程可复算但不够稳定
- 指标能复算，但缺少严格“指标 -> 分数”固定映射时，会出现评分漂移。

## 3. 重构目标（必须同时满足）
1. 五概念评分全部提升到 9 分
- 评分兼容视图：`focus`、`plan`、`task`、`action`、`memory`
- 运行时最小模型：`focus`、`task`、`context`（`trigger` 与 `evidence` 作为属性层）

2. 架构保持简洁优雅
- 概念更少、语义更清楚、职责边界更稳

3. 心智负担低
- 用户无需理解内部调度细节，也能稳定获得正确结果

4. 响应更快、token 成本更低
- 上下文更精确、执行更少重跑、整体吞吐更高

5. 核心能力不退化
- 特别是 `cron` 必须保留且增强，不得削弱

## 4. 不可妥协约束
1. 非词表驱动
- 核心能力（意图判定、路由、状态迁移）不得依赖关键词硬编码。
- 必须使用结构化信号、模型判别、规则化状态机。

2. `cron` 是 P0
- 必须保留 `cron`/`scheduled_at`/`on_worker_slot_freed` 的能力表达。
- 必须可追踪、可审计、可恢复。

3. 低心智负担
- 不允许引入新概念堆叠来“修复概念问题”。
- 优先统一模型，而非增加平行机制。

4. 可验证优先
- 所有“已完成/已处理”必须可追溯到系统动作证据。

5. Schema-First
- 核心对象先定义统一 JSON Schema，再允许进入执行与评估。
- 无 Schema 版本、无兼容声明、无迁移边界的对象禁止进入主流程。

## 5. 统一工作模型（最终形态）
采用统一闭环模型 `Workstream Loop`：

- `focus`：工作线主键（唯一归属）
- `task`：执行单元（一次可交付动作，回传 `task_evidence`）
- `context`：持久上下文（长期事实 + 连续性账本）
- `trigger`：触发属性（手动/定时/事件），不单独扩张为核心对象
- `evidence`：任务证据属性（含 `state_delta`），不单独扩张为核心对象

统一闭环：
用户意图 -> 结构化意图包 -> 触发 -> 任务执行 -> 任务证据 -> 上下文更新

## 6. 五概念评分兼容视图（9 分标准）
说明：本节用于评分与回归兼容，不要求运行时保留五个一等对象。
### 6.1 focus
目标：从标签升级为“强约束路由主键”。

达成条件：
- 多工作线场景中不存在模糊回落。
- 关键对象（task/plan/history/choice）可追溯到唯一工作线。
- 跨线误路由成为低频异常，而非常态风险。

### 6.2 plan
目标：从“复杂语义容器”收敛为“可控触发器”。

达成条件：
- 触发语义清晰、可重复、可暂停恢复。
- 与工作线强绑定，避免跨线触发污染。
- 重复触发与空转被显著压制。

### 6.3 task
目标：保持“执行单元”的稳定职责。

达成条件：
- 生命周期完整且可对账。
- 结果可追溯、可归档、可验真。
- 取消/恢复行为可解释，不造成大规模浪费。

### 6.4 action
目标：作为评估维度反映“任务证据中的状态迁移质量”。

达成条件：
- 意图到证据映射稳定，闭环可验证。
- 关键状态变化可从 `task_evidence.state_delta` 审计。
- “回复正确但动作错误”显著下降。

### 6.5 memory
目标：只保留长期事实，不承担过程调度。

达成条件：
- 记忆污染降低，命中质量提升。
- 记忆与历史/事件职责分离。
- 记忆条目更少但更有用。

## 7. 意图系统目标（非词表）
引入“结构化意图包”作为唯一调度输入形态（能力要求，不是实现细节）：
- 意图类型
- 目标对象
- 目标工作线
- 预期状态迁移
- 置信度
- 证据引用

目标：
- 降低主观解释空间
- 降低口头确认与真实执行不一致
- 提升回归可测性
- 与 JSON Schema 严格对齐

## 8. 上下文与成本治理目标
### 8.1 问题来源
- 当前上下文预算存在分配失衡与不可解释的裁剪结果。
- 高价值语义可能被过度压缩，低价值片段占用预算。

### 8.2 治理目标
- 总预算固定上限
- 预算决议可直接记录与复盘
- 预算优先投给“当前工作线 + 当前任务 + 最近结果”
- 计划/任务关键语义不再被过度截断
- 记忆注入持续“少而精”

### 8.3 业务预期
- P95 响应时延下降
- token 中位数下降
- 误判与重跑成本下降

## 9. 稳定性与恢复目标
1. provider 波动
- 先健康门控再调度，避免失败-重建循环。

2. 状态一致性
- 任何开始与结束都要对账，杜绝长期悬挂。

3. 取消与恢复
- 优先保留可复用状态，减少已投入成本浪费。

4. 降级策略
- 异常阶段优先“稳定与收敛”，而非功能扩张。

## 10. 用户体验目标
- 用户表达目标即可推进，不需学习内部状态。
- 多工作线冲突时，系统解释清楚且最小打扰。
- 输出以证据为主，不以模板化话术替代执行事实。

## 11. 评分与验收体系（与验证文档一致）
重构完成判定必须满足：

1. 五概念评分
- `focus/plan/task/action/memory >= 9.0`

2. 运行指标
- `task_success_rate >= 95%`
- `intent_done_rate >= 92%`
- `route_correct_rate >= 98%`
- `progress_integrity_rate >= 99%`
- `continuity_contract_match_rate >= 98%`
- `manager_reask_rate <= 8%`
- `context_waste_ratio <= 20%`
- `P95 manager response` 分档达标：
- `lite(5k~8k) <= 2.0s`
- `standard(8k~12k) <= 2.5s`
- `heavy(12k~20k) <= 3.2s`
- `token median` 较基线下降 `>= 30%`

3. 稳定性
- 同窗口重复评分结果波动在稳定阈值内
- 评分漂移可解释且可追溯

## 12. 分阶段推进策略（非实现层）
### 阶段 1：语义收敛
- 建立结构化意图与工作线强约束
- 目标：先消除错线与误执行

### 阶段 2：状态统一
- 统一 `task_evidence` 证据语义与状态迁移审计
- 目标：提升可验证性与可审计性

### 阶段 3：成本优化
- 重分配上下文预算并固化预算上限
- 目标：提升响应速度并降低 token 消耗

### 阶段 4：放量验证
- 按稳定评分体系做回归对照
- 目标：满足门槛后再扩大范围

## 13. 本轮对话形成的关键决策（必须保留）
1. 不采用词表驱动作为核心机制
2. `focus` 必须从弱标签升级为强约束路由
3. `cron` 必须保留且列为重点能力
4. 上下文裁剪阈值需要重新分配
5. 验证评分流程必须可复现、可稳定
6. 最终方案文档将作为后续重构基准，不依赖临时口头共识

## 14. 边界声明
本文件明确不包含：
- 代码结构
- 函数级实现
- 模块级技术选型
- 兼容层设计

本文件只定义“最终应达到的系统能力与约束”。

## 15. 风险与防偏离机制
1. 风险：重构过程概念反弹（越改越复杂）
- 防偏离：每次方案评审先检查“概念是否新增、是否可合并”。

2. 风险：性能优化侵蚀语义正确性
- 防偏离：先守路由正确率与闭环率，再追求时延/token。

3. 风险：评分体系被临时解释污染
- 防偏离：评分口径版本化，人工裁决受上限约束。

4. 风险：`cron` 在结构重排中被边缘化
- 防偏离：`cron` 纳入 P0 回归清单，单独验收。

## 16. 成功定义
重构完成的标志不是“代码改完”，而是：
- 五概念评分稳定达到 9 分
- 关键指标持续达标
- 用户感知到更少干预、更高可预期性、更低等待成本
- 文档可独立指导后续迭代与回归


## 17. 术语与语义约定
为避免重构期间同词异义，本节固定术语解释：

- 工作线（Workstream）：围绕同一业务目标持续推进的一组任务与状态。
- 触发器（Trigger）：让某工作线进入下一轮调度的条件。
- 执行单元（Execution Unit）：一次可交付、可验证、可归档的工作动作。
- 状态迁移（State Transition）：系统状态发生变化的唯一合法入口。
- 长期事实（Durable Facts）：跨轮次仍有效、可被后续决策复用的信息。
- 动作证据（Action Evidence）：证明系统确实执行了某变更的事件与状态记录。

## 18. 范围界定（In / Out）
### 18.1 In Scope
- 五概念语义统一与关系重塑
- 意图判定的结构化输入与调度收敛
- 多工作线路由一致性治理
- `cron`/计划触发链路稳定性增强
- 上下文预算重分配与成本治理
- 评分体系稳定化与回归基线建立

### 18.2 Out of Scope
- 具体代码拆分策略
- 具体模型供应商选型
- 前端视觉与交互重设计
- 与目标无直接关系的新功能扩展

## 19. 状态机语义（产品级）
本方案要求所有核心对象遵循一致状态语义：
- `idle`：等待触发，未占用执行资源
- `active`：当前在推进或可立即推进
- `blocked`：被外部条件阻塞，需明确阻塞原因
- `done`：本轮目标完成并可审计

状态迁移必须满足：
1. 迁移可解释（有原因）
2. 迁移可追溯（有证据）
3. 迁移可恢复（存在下一步）

## 20. 关键业务场景矩阵（验收视角）
### 20.1 单工作线持续推进
期望：
- 无多余确认
- 触发与执行稳定
- 结果可追溯

### 20.2 多工作线并行推进
期望：
- 不串线
- 不误抢优先级
- 冲突可解释

### 20.3 用户控制类指令（暂停/恢复/取消）
期望：
- 执行一致
- 反馈明确
- 无隐性继续运行

### 20.4 provider 波动与外部失败
期望：
- 优先降级而非重跑风暴
- 失败原因可定位
- 能恢复而不丢关键状态

### 20.5 `cron` 驱动场景
期望：
- 定时触发不退化
- 触发与工作线绑定
- 触发后行为可审计

## 21. 上下文治理详细目标
### 21.1 治理原则
- 上下文不是越多越好，而是越相关越好。
- 所有注入都应服务“当前轮次决策”。

### 21.2 预算策略目标
- 固定总预算上限
- 预算决议固定且可直接追溯
- 高价值段落优先保留
- 低价值噪音优先淘汰

### 21.3 质量目标
- 关键信息不被截断导致误判
- token 消耗下降同时不牺牲正确率
- 响应时延改善不依赖牺牲可解释性

## 22. `cron` 保真协议（P0）
1. 能力保真
- 保留 `cron`、`scheduled_at`、`on_worker_slot_freed` 三类触发语义。

2. 行为保真
- 触发条件、触发时序、触发后动作都必须可追溯。

3. 结果保真
- 触发成功率、重复触发抑制、误触发率纳入固定回归项。

4. 风险保真
- `cron` 任何退化必须阻断发布。

## 23. 评分体系治理要求
1. 评分系统本身也是被治理对象。
2. 指标定义、公式、权重、分档必须版本化。
3. 人工裁决必须受上限约束并附证据。
4. 评分不可仅用于“展示”，必须直接驱动重构优先级。

## 24. 决策记录与追踪机制
每次方案变更必须写入决策记录（ADR 风格，文档级要求）：

- 备选方案
- 最终选择
- 影响范围
- 风险与回滚条件

## 30. Manager/Worker 连续主题治理（强契约隔离）
### 30.1 问题定义
- 当前 `manager` 与 `worker` 隔离导致“交接弱化”，表现为：
- 目标语义在下发时变形，执行完成后难以核对。
- 连续主题任务中，上一轮关键结论未被下一轮稳定继承。
- 用户感知为“看似在同一话题，实际每轮都在重启”。

### 30.2 治理原则
- 隔离保留：分层职责不合并，仍保持编排与执行分离。
- 契约增强：每次下发与回收都必须遵循统一契约。
- 证据优先：无证据不判完成，无对账不进入下一轮。
- 单线优先：默认单活跃工作线，减少并行噪音与抢占。

### 30.3 下发契约（Manager -> Worker）
- 必须包含：`focus_id`、本轮目标、完成判据、禁止偏航边界、必要上下文切片引用。
- 必须明确：本轮只处理什么，不处理什么。
- 必须可审计：每个完成判据都可在回收阶段逐条核对。

### 30.4 回收契约（Worker -> Manager）
- 必须包含：已执行动作、结果证据、未完成项、风险、建议下一步。
- 必须对应：逐条映射下发判据，不允许“只给结论不对应判据”。
- 必须可延续：回收内容能直接成为下一轮最小连续上下文。

### 30.5 连续性账本（Continuity Ledger）
- 定位：不是长历史，不是知识库，而是“当前主题的最小连续状态”。
- 仅保留：
- 最近有效决策
- 当前未闭环事项
- 用户硬约束与不可妥协边界
- 近轮失败原因与禁止重犯项
- 使用要求：
- manager 每轮优先读取账本再决策
- worker 回收后先更新账本再结束轮次

### 30.6 回收闸门（Manager Gate）
- 闸门校验项：
- 是否仍在原 `focus`
- 是否满足全部完成判据
- 是否出现越界动作
- 是否需要澄清后再推进
- 任一项不满足：进入返工或澄清，不得直接标记完成。

### 30.7 与 `cron` 的一致性要求
- `cron` 触发后的任务也必须走同一契约与闸门。
- `cron` 不享受“跳过对账”的特殊路径。
- 定时续跑必须继承同一 `focus` 与连续性账本。

## 31. Manager 上下文长度矛盾治理（短上下文保细节）
### 31.1 矛盾定义
- 上下文太短：细节缺失，连续主题能力下降。
- 上下文太长：噪音增大、延迟上升、token 成本失控。
- 目标不是“更长”或“更短”，而是“足够且干净”。

### 31.2 治理目标
- manager 每轮预算稳定落在 `5k~20k`。
- 默认场景落在 `5k~12k`，仅重场景升档。
- 细节可按需拉取，不做全量常驻注入。
- 预算变化可解释，不允许无原因放大。

### 31.3 三层上下文模型（非实现语义）
- L0 决策胶囊（必带）：
- 当前 `focus`、当前任务判据、最近结果证据、连续性账本摘要。
- L1 关联片段（按需）：
- 与本轮决策直接相关的历史片段与约束。
- L2 细节档案（引用）：
- 完整过程细节与长证据，默认不注入，仅在冲突/追责/复核时拉取。

### 31.4 注入优先级
- 最高优先：当前轮决策必需信息（不注入则会误判）。
- 中优先：影响本轮动作边界的信息。
- 最低优先：仅用于解释背景但不影响决策的叙述信息。

### 31.5 淘汰规则
- 先淘汰重复叙述，再淘汰低价值背景，再淘汰过期细节。
- 不得淘汰：用户硬约束、未闭环事项、最近失败原因。
- 任何淘汰必须保持“可恢复引用”，避免永久丢失。

### 31.6 升降档规则
- 升档触发：
- 多任务冲突
- 关键判据缺证据
- 高风险回滚窗口
- 降档触发：
- 连续两轮无冲突且判据齐全
- 无新增高风险依赖
- 未发生跨线争议

### 31.7 质量守恒约束
- 禁止用“压缩到不可判定”来换 token 指标。
- 禁止用“全量注入”来换正确率指标。
- 速度、成本、正确率必须同时满足门槛。

### 31.8 观测指标
- `manager_reask_rate`：因缺上下文导致的重复澄清比例。
- `context_waste_ratio`：注入但未参与决策的上下文比例。
- `detail_recall_success_rate`：按需拉取细节后的一次判定成功率。
- `context_budget_drift`：预算偏离设定档位的比例。

## 32. OpenClaw 参考结论的吸收边界（产品策略）
### 32.1 应吸收部分
- 先结构化归属，再语义推进。
- 会话归属键稳定优先，减少串线与跳线。
- 线程/渠道/身份等结构化信号优先于主观主题猜测。

### 32.2 不直接照搬部分
- 不把系统停留在“只稳归属、弱推进”。
- 必须补足 `focus/task/context` 的闭环与证据化能力。
- 不牺牲 `cron` 的触发表达与审计能力。

### 32.3 统一原则
- L1 借鉴 OpenClaw：稳定归属、低成本、低抖动。
- L2 落地本方案：闭环推进、连续性治理、评分可回归。
- 以更少概念实现更高完成质量，而非机制堆叠。

## 33. 最终承诺
后续大规模重构必须围绕以下四条主线推进：
1. 语义一致（概念少且定义稳）
2. 执行可证（动作与结果有证据）
3. 成本可控（速度与 token 同时优化）
4. 能力不退（尤其 `cron`）

若任一主线被破坏，重构视为未完成。

## 34. 一次性并入治理包（本轮新增）
本节为本轮确认的“10 项一次性补充”，要求与既有章节并行生效，不得选择性忽略。

### 34.1 Schema 治理（Schema Governance）
- 所有核心对象采用 `schema_version` 显式标记。
- 版本规则：`major` 表示不兼容变更，`minor` 表示兼容扩展。
- 每次 Schema 变更必须记录：变更项、影响对象、预计回归影响、回滚条件。
- 禁止“未登记字段”在主链路默默生效。

### 34.2 状态迁移契约（State Migration Contract）
- 重构期间必须定义旧状态到新语义的一次性迁移边界。
- 迁移要求：
- 可追溯：每条迁移可回查来源与目标。
- 可验证：迁移后状态可通过固定规则校验。
- 可终止：不允许长期“新旧并存且互相写入”。
- 验收要求：迁移后关键对象不存在“双重真值”。

### 34.3 确定性路由不变量（Deterministic Routing Invariants）
- 同一结构化输入在同口径下必须得到同一 `focus_key`。
- 冲突信号处理优先级必须固定，不允许运行时漂移。
- 路由回退路径必须可解释，并记录回退原因。
- 目标：把“串线”从常态风险降为异常事件。

### 34.4 下发完整性闸门（Task Contract Completeness Gate）
- manager 下发前必须通过契约完整性校验。
- 必填项缺失（目标、判据、边界、引用）即禁止派发。
- 禁止“先执行后补判据”。
- 目标：降低 manager/worker 语义损耗与返工。

### 34.5 证据质量闸门（Evidence Quality Gate）
- worker 回收必须逐条对应完成判据。
- 仅有结论、无证据引用不得记为完成。
- 证据冲突时优先进入复核，不允许直接推进下一轮。
- 目标：消除“口头完成”。

### 34.6 上下文预算控制器（Context Budget Controller）
- 固定总预算上限，section 预算直接取自 `manager.promptSections`。
- 预算决议以 `manager_context_budget_resolved` 显式记录，不再引入档位升降。
- 任何裁剪结果都必须能从最终 `promptSectionLimits` 直接复盘。
- 目标：稳定速度、成本与正确率三者平衡。

### 34.7 `cron` 可靠性 SLO（Cron Reliability SLO）
- `cron` 作为 P0 能力，单列可靠性目标：
- 触发成功率
- 重复触发抑制率
- 误触发率
- 触发到动作延迟分位
- 任一 SLO 退化超过阈值，阻断发布。

### 34.8 回放集与金标集（Replay & Golden Set）
- 固定最小回放集覆盖：
- 模糊意图输入
- 跨主题切换
- 长链连续任务
- `cron` 触发与恢复
- 固定金标口径：同窗口、同版本、同输入必须得到可复现评分区间。

### 34.9 No-Go 硬闸门（Hard Gates）
- 以下任一不满足即 `No-Go`：
- 路由正确率未达标
- 连续性契约匹配率未达标
- 证据质量闸门未通过
- `cron` SLO 未达标
- 评分稳定性未达标
- 目标：防止“带病放量”。

### 34.10 运行手册（Operational Runbook）
- 必须具备：
- 故障分级标准
- 人工接管触发条件
- 回滚条件与责任归属
- 复盘模板与时限要求
- 目标：从“可设计”升级到“可运营”。

### 36.2 关键策略约束（已编码）

2. 连续主题安全性
- 同主题更新时，旧任务不会被静默复用为“已满足新判据”。
- 新任务保留新 contract，后续 evidence 必须按新判据回收。

### 36.3 与方案边界的关系
1. 未引入新增一等对象
- 运行时仍保持 `focus/task/context` 最小模型，`trigger/evidence` 为属性层。

2. 不依赖词表驱动
- contract/evidence/focus 相关判定均为结构化字段或状态逻辑，不是关键词列表匹配。

3. `cron` 不降级
- 本轮变更没有削弱 cron 语义；反而提升了可观测性。
