# 实施归档：基于 coding agent 调研的最小优化落地

日期：2026-03-28
任务：`task-100f067bf3f84930bb57ca275f0e940d`

## 结论先行

- 本轮选择落地的唯一优化项是：为 worker prompt 注入显式 `runtime_contract`，把当前任务的 `resource_mode`、实际 `working_directory`、可选 `task_cwd`、`worktree_root`、`branch` 直接暴露给执行面。
- 该改动直接对应调研中的“显式 runtime 权限合同”，但不新增 manager 协议、不扩展调度层、不引入第二套审批或 runtime 抽象。
- 这是一项收紧边界表达的改动，不改变现有 task 创建、dispatch、handoff 或 review gate 主流程，因此不会明显削弱现有能力。

## 候选方向与取舍

### 候选 A：worker prompt 显式 runtime 合同

- 现状缺口：worker system prompt 已强调证据优先级与 handoff 协议，但没有稳定写出当前任务到底是只读还是可写，也没有明确 worktree/branch 事实。
- 收益：减少执行面误判路径和权限边界的空间，且完全复用现有 `Task.resourceMode`、`Task.git`、`workspaceDir`。
- 成本：只涉及 worker prompt 组装、模板与最小测试，边界最小。

### 候选 B：新增任务自治级别枚举

- 优点：更接近调研中的“自动化等级”表达。
- 本轮不选原因：需要扩 manager schema、执行合同、文档和校验链路，但当前运行时并没有新的自治能力真正消费这个枚举，容易先长协议、后补实现。

### 候选 C：review gate read model / WebUI 收紧

- 优点：也符合调研中的 review queue 方向。
- 本轮不选原因：会跨 read-model / WebUI，多模块联动，容易扩成产品面改动，不符合“本轮只做一个最小高 ROI 闭环”。

## 简明自评审

### 为什么符合项目目标

- `mimikit` 的主线目标是保持极简编排层，把具体执行交给外部运行时，同时收紧状态与合同边界。
- 本轮改动只增强执行合同的明确性，没有把主线程扩成执行平台，也没有把消息历史重新做成真相源。

### 为什么不过度设计

- 没有新增持久化字段，没有新增 action，没有新增运行时 profile。
- 只把已有真实状态重新组织成 worker 可读合同。

### 为什么不会明显削弱现有能力

- 原有 prompt、resume、focus、handoff 协议全部保留。
- 只读任务和 worktree 写任务都获得更清晰的边界表达；原有非 worktree 写任务仍按既有路径执行。

### 为什么暂不处理其他候选

- 任务自治级别枚举：当前会先扩大协议面，再倒逼实现，ROI 不成立。
- review gate/UI 收紧：更适合下一轮单独任务处理，而不是与执行合同改动并行。

## 风险与边界

- `runtime_contract` 目前只做边界显式化，不会阻止运行时本身的更高权限；真正的权限 enforcement 仍由既有 sandbox / worktree / task mode 路径决定。
- `working_directory` 与 `task_cwd` 会同时出现于“仓库根执行 + 子目录 task”场景；这是刻意保留的真实差异，不做额外抽象层包装。
