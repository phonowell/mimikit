# 实施归档：压缩 `plan.effect.taskTemplate` 的最小闭环

日期：2026-03-28
任务：`task-4c056e6e354b422ea722ff6fc44ec476`

## 结论先行

- 本轮选择落地的唯一整改项是：删除 `plan.effect.taskTemplate.semanticKey` 的重复持久化，只保留 `fingerprint` 作为 plan 去重所需的单一稳定 digest。
- 该改动直接对应路线图任务 3 的最小闭环：收紧 `plan.effect.taskTemplate`，但不并发重做 plan payload、SSE/WebUI 投影或 manager 主链。
- 现有 enqueue、plan 替换、snapshot 持久化与 manager 可见合同摘要能力均保持不变，没有明显削弱现有能力。

## 候选方向与取舍

### 候选 A：压缩 `plan.effect.taskTemplate`

- 现状缺口：`taskTemplate` 同时持有 `executionSpecId`、`contract`、`fingerprint`、`semanticKey`、`cwd` 等字段，其中 `semanticKey` 未被任何运行时路径消费，只在类型、schema 与测试夹带。
- 收益：直接减少 plan snapshot 的重复语义，且不需要扩 manager/worker 协议。
- 成本：只涉及 plan effect 构建、类型/schema 与最小测试夹具，边界最小。

### 候选 B：只读盘点 projection 边界

- 优点：是路线图中的必要前置研究。
- 本轮不选原因：它是只读任务，不能满足“继续落地一项高优先整改”的当前合同。

### 候选 C：直接收窄 SSE/WebUI projection

- 优点：业务收益明显。
- 本轮不选原因：路线图明确要求先完成任务 4 的只读盘点，再进入该写任务；现在硬做会把任务扩成多主题并行重构。

## 简明自评审

### 为什么符合项目目标

- 改动只收紧 plan 持久化合同，不把主 agent 扩成更重的编排层，也不新增第二套状态载体。
- 这与“文件系统为真相源、主线程只保留高价值上下文”的方向一致。

### 为什么不过度设计

- 不改 plan trigger 模型。
- 不新增兼容层或迁移壳。
- 不重写 prompt payload，只删除当前未被消费的重复字段。

### 为什么不会明显削弱现有能力

- `fingerprint` 仍保留，`buildPlanEffectKey()` 的 plan 去重逻辑不变。
- `executionSpecId` 与 `contract` 仍保留，plan 触发与 manager 可见合同摘要能力不变。
- `semanticKey` 仍会在真正创建 Task 时按既有逻辑生成；只是 plan 侧不再提前重复持久化。

### 为什么暂不处理其他候选

- 去掉 `contract` 会连带影响 plan prompt/history payload，需要额外设计从 spec 派生摘要的链路，边界会扩大。
- 去掉 `fingerprint` 会迫使 plan 去重键改成异步 spec 读取或另一套 digest，本轮 ROI 不够高。

## 风险与边界

- 本轮只删除 `semanticKey` 这一项重复持久化，`contract` 仍保留在 plan effect 中；更进一步的压缩应单独评估 prompt/history 摘要链路。
- 当前变更依赖“plan 侧不消费 `semanticKey`”这一事实；若后续为 plan 新增语义去重场景，应重新评估是否需要新的单一 digest，而不是恢复多字段并存。
- 为避免破坏已有状态文件，本轮对 legacy runtime snapshot 中残留的 `semanticKey` 做了解析期归一化；这不是恢复旧契约，而是一次性吸收旧字段并向新契约收口。
